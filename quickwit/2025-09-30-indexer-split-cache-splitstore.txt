    - 정기적으로 서비스를 재시작하여 임시 파일 정리
    - 디스크 사용량을 외부에서 모니터링
    - 충분한 디스크 공간 확보
    - 인덱싱 파이프라인이 정상적으로 완료되면 임시 파일은 자동으로 정리되므로, 파이프라인이 정상 작동하는지 확인

⏺ Kafka로 지속적으로 데이터를 컨슘할 때 임시 파일이 정리되는 시점은:

  1. commit_timeout_secs (기본값: 60초) - 매 60초마다 split이 commit되어 스토리지로 업로드됩니다. 업로드가 완료되면 해당 split의 로컬 임시 파일은 삭제됩니다.
  2. split_num_docs_target에 도달 시 - 설정된 문서 수에 도달하면 즉시 split을 commit하고 업로드합니다.
  3. TempDirectory가 Drop될 때 - 각 split은 TempDirectory 구조체로 관리되며, split 처리가 완료되어 이 객체가 drop되면 디렉토리가 자동으로 삭제됩니다.

  따라서 Kafka처럼 지속적으로 데이터가 들어오는 경우:
  - 정상 작동 시: 60초마다 또는 문서 수 제한에 도달할 때마다 split이 업로드되고 임시 파일이 정리됨
  - 문제 발생 시: 업로드 실패, 네트워크 문제 등으로 split이 계속 로컬에 쌓일 수 있음
  - 서비스 재시작: /indexing 디렉토리 전체가 비워짐

  결론적으로, 정상적으로 작동한다면 주기적으로 정리되지만, 장애 상황에서는 디스크가 가득 찰 위험이 있습니다.

⏺ downloaded-splits 디렉토리는 다음과 같이 정리됩니다:

  1. Merge 작업 완료 시 자동 삭제:
    - downloaded_splits_directory는 MergeScratch 구조체의 TempDirectory 필드입니다
    - MergeScratch가 drop될 때 (merge 작업이 완료되거나 실패할 때) 자동으로 삭제됩니다
    - TempDirectory는 Rust의 RAII 패턴을 사용하여 스코프를 벗어나면 자동으로 디렉토리를 삭제합니다
  2. 디렉토리 구조:
  /indexing/
    └── merge/
        └── downloaded-splits/  <- merge 완료 시 자동 삭제
  3. 정리 시점:
    - 정상 완료: Merge 작업이 성공하고 새로운 split이 업로드되면 즉시 삭제
    - 실패 시: Merge 작업이 실패해도 MergeScratch 객체가 drop되면서 삭제
    - 서비스 재시작: /indexing 전체가 비워지므로 함께 삭제

  따라서 downloaded-splits는 merge 작업 단위로 관리되어, 각 merge 작업이 끝나면 (성공/실패 여부와 관계없이) 자동으로 정리됩니다. 이는 indexer-split-cache와 달리 임시 작업 공간으로만 사용되고 즉시 정리되는 구조입니다.

⏺ split 크기가 계속 증가하는 이유를 찾았습니다:

  1. get_cached_split 호출 시 캐시에서 제거:
    - Merge 작업을 위해 split을 가져올 때, 캐시에서 move_out으로 이동시킵니다
    - 이는 "optimistically assume that this is for a merge operation that will be successful" 라고 코드에 명시되어 있습니다
  2. 문제 상황:
    - Merge가 실패하거나 중단되면 split이 캐시에서 제거되었지만 다시 돌아오지 않습니다
    - 다음 merge 시도 시 캐시 미스가 발생하고, remote storage에서 다시 다운로드합니다
    - 이렇게 다운로드된 split은 downloaded-splits 디렉토리에 저장됩니다
  3. 누적되는 경우:
    - Merge 작업이 반복적으로 실패하거나
    - Merge 작업이 매우 느리게 진행되거나
    - 네트워크/스토리지 문제로 split 업로드가 실패하는 경우
  4. 캐시 제한이 적용되지 않는 이유:
    - downloaded-splits는 캐시 외부의 임시 디렉토리입니다
    - split_store_max_num_bytes 제한은 캐시에만 적용됩니다
    - 따라서 merge 작업 중 다운로드된 split들은 이 제한에 영향받지 않습니다

  해결 방법:
  - Merge 작업이 정상적으로 완료되는지 확인
  - 네트워크/스토리지 연결 상태 확인
  - Merge 정책 조정 (너무 자주 또는 너무 큰 merge 방지)
  - 충분한 디스크 공간 확보

    - Actor가 무한정 대기하거나 멈춰서 handle 함수가 완료되지 않음
    - Arc reference count가 0이 되지 않음
    - OS 레벨에서 디렉토리 삭제 실패 (권한, 열린 파일 등)
